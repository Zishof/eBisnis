Root cause: $2 (body.status, plain JS string) is used both as a direct column
value and inside several unqualified string-equality CASE WHEN comparisons.
node-postgres sends parameters untyped (OID 0/"unknown"); Postgres's parser
must infer a single consistent type for $2 across every occurrence in the
statement and failed to do so, throwing "inconsistent types deduced for
parameter $2" (bilingual message: "mededuksi tipe yang tidak konsisten untuk
parameter $2"). This made the ENTIRE price-book transition endpoint --
submit, approve, reject, deactivate -- fail with HTTP 500 on every call
against real Postgres. Fix: explicit ::varchar cast on every occurrence.

Bug A root cause: same "inconsistent types deduced for parameter $6" class
as Bug D -- $6 (Math.abs(variance), a JS number) is used both as the raw
`quantity` column value and inside unqualified `$6 < 0` / `$6 > 0`
comparisons. Fixed with explicit ::numeric casts.

Bug B root cause (only exposed once Bug A's exception was fixed and the
statement could actually run): the CASE WHEN direction logic compared $6 --
which is Math.abs(variance), therefore ALWAYS >= 0 -- against < 0 and > 0 to
decide whether the warehouse goes in source_warehouse_id or
destination_warehouse_id. Since $6 can never be negative, "$6 < 0" is always
false and "$6 > 0" is always true (variance=0 rows are filtered out by the
WHERE clause upstream) -- every adjustment, whether ADJUSTMENT_IN (found
more stock) or ADJUSTMENT_OUT (found less stock), was recorded with the
warehouse in destination_warehouse_id, never source_warehouse_id. This
silently breaks the "balance = Sigma(movement)" invariant that is the core
claim of screen 8/9 for every ADJUSTMENT_OUT ever posted. Fixed by adding a
14th bound parameter carrying the *signed* variance, used only for the
direction decision, while $6 (the always-non-negative magnitude) still feeds
the `quantity` column, which itself must always be a non-negative value.

BUG C fix -- buildReport() parameter binding (~line 2017, private method)
=========================================================================
BEFORE:
    const report = reportSql(code, S);
    if (!report) throw AppError.badRequest(ErrorCodes.VALIDATION_FAILED, `Kode laporan ${code} tidak didukung.`);
    const rows = await this.tenantDb.query<Record<string, unknown>>(schemaOf(user), report.sql, [asOfDate]);

AFTER:
    const report = reportSql(code, S);
    if (!report) throw AppError.badRequest(ErrorCodes.VALIDATION_FAILED, `Kode laporan ${code} tidak didukung.`);

Root cause: buildReport() (backs both `POST /reports/:code/preview` and
`POST /reports/:code/snapshot`, used by screens 10 and 13-16) unconditionally
binds `[asOfDate]` to every report query. Three of the ~17 report codes in
`reportSql()` -- 'stock-list' (screens 14/15's report), 'supplier-list', and
'customer-list' -- have zero `$1` placeholders in their SQL. Postgres
rejected every call to those three report codes with "bind message supplies
1 parameters, but prepared statement requires 0" (HTTP 500). Fixed by only
including the parameter when the SQL text actually references $1.
